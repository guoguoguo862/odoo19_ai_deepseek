# Odoo 19 AI 网站购物助手：客户会议讲稿与演示指南

**编制：Suto｜版本：1.3｜日期：2026-11-16｜依据：Odoo 19 企业版、独立 `ai_deepseek` 与 `ai_sale_order_2nd` 实现**

本文适合产品负责人、实施顾问和销售人员使用。建议安排 **约 21 分钟说明（可调整为 20～23 分钟）、5 分钟演示、5 分钟问答**。会议材料描述的是当前已经开发的功能，包含客户经常选择的 DeepSeek 模型接入方案；标明“扩展方向”的内容需要另外开发和验收。

本次会议最需要传达的一句话是：

> 客户在网站聊天框中说出想买的商品、数量和规格，AI 帮助理解需求，Odoo 查询真实商品并更新当前购物车，客户再按网站标准结账流程核对和付款。

## 一、会前准备

介绍功能来源时可以直接说：**“网站聊天框、AI Agent 对话和工具调用机制来自 Odoo 19 企业版原生模块；我们通过独立 `ai_deepseek` 接入模型，通过 `ai_sale_order_2nd` 提供查询商品、加入购物车等业务工具。”** 原生框架需要安装和配置；本项目没有另外重写聊天界面。适配已从企业版核心拆出，客户交付包括两个独立模块及相应配置。

会议前由实施或开发人员在测试环境完成以下准备。演示人员不需要在客户面前展示密钥或系统参数。

1. 确认网站页面能打开，聊天入口关联的 Agent 正常接收新消息。曾经转接人工的旧聊天可能已经停止自动调用 AI，演示宜使用事先验证的新会话。
2. 确认当前 Agent 使用的模型与相应 API 凭据匹配。`ai_deepseek` 从 DeepSeek `/models` 获取并缓存实际型号，选择已通过现场演练的型号；这不是对所有 Odoo 安装环境的默认配置说明。
3. 确认 Agent 关联 `Website Cart Ordering` 主题，主题包含商品搜索与加入购物车两个工具。
4. 使用已验证的测试账号，在同一浏览器、同一 Odoo 网站内操作。准备好聊天页与 `/shop/cart` 页面，避免浏览器无痕窗口、不同域名或不同账号的会话混用。
5. 检查演示商品仍为已发布、可销售且可在当前网站加购的商品。示例引用当前测试目录，客户正式商品应重新验收。
6. 记录演示前购物车内容；可在标准购物车界面手工清空测试商品。每个演示场景前重新核对，避免把“再次增加数量”误认为系统重复下单。
7. 预先执行一次真实自然语言演示，记录当前模型响应时间。保留一组脱敏的成功聊天与购物车截图，供网络或模型服务异常时解释流程。
8. 只演示加入购物车、核对商品和进入结账步骤；本次演示不进行真实支付，不确认真实业务订单。
9. 若演示客户自建环境，确认 `ai_deepseek` 和 `ai_sale_order_2nd` 已安装，客户在 AI 设置配置并保存自己的 Key，模型目录同步成功，Agent 从目录选择型号且无 Sources。企业版核心无需增加 DeepSeek 修改；仅复制购物模块仍不会提供模型适配或原数据库 Key。
10. 如讨论模型成本，准备供应商当日价格与实际使用账单。区分输入、缓存命中、输出等计费项，记录完成一次正确加购需要的调用轮数，不使用无来源的固定价格或节省比例。

推荐演示商品：

| 场景 | 当前测试目录示例 | 说明 |
| --- | --- | --- |
| 唯一商品 | 黑色抽屉，参考号 `FURN_8900` | 已验证“帮我下单一个黑色抽屉”的自然语言流程 |
| 精确商品 | `DESK0005`、`DESK0006` | 参考号指向具体变体；适合演示已知型号的批量加购 |
| 规格识别 | `Two-Seat Sofa (Velvet)` | 演示英语目录与中文材质描述衔接 |
| 存在歧义 | 白色可定制化桌子 | 当前目录有多种材质等属性，需要进一步确认具体变体 |

## 二、约 21 分钟讲解稿

以下每段都可直接用于口头讲解。代码名称是给演示人员理解的辅助信息，面对非技术客户时不必逐个朗读。

### 第 1 段：功能解决什么问题，约 2 分钟

“客户到网站购物时，常常知道自己想要什么，但未必知道商品在目录中的准确名称，也可能不熟悉产品筛选入口。例如客户只说‘要一个黑色抽屉’，人工客服通常需要先理解他的意思、找到实际商品，再帮助他进入购买流程。

“这次我们把这段过程接到了 Odoo 网站的聊天框中。客户用正常语言表达需求，购物助手帮助查找商品、识别规格和数量，能够确定时把商品加入购物车。客户仍然可以打开购物车检查真实商品、数量和金额，并按网站原有结账流程完成后续操作。

“它的直接价值是减少查目录、问型号和来回切换页面的步骤。是否提高成交率、减少多少客服工作量，需要在上线后用实际业务数据评估，我们会把这些作为可跟踪的指标。”

### 第 2 段：AI 与 Odoo 各自负责什么，约 3 分钟

“我们可以把它理解为两个角色合作。AI 更擅长理解客户的话：客户是在询价、找商品，还是明确要求加购；提到的是哪种商品、什么颜色、买几件；哪些信息已经提供，哪些规格还不明确。

“Odoo 则负责真实业务。商品是否存在、是否已发布、当前网站能否销售，以及购物车最终发生什么变化，都由我们预先开发的业务工具和 Odoo 标准商城逻辑处理。

“例如‘一个’会被理解为数量 1，但 AI 不能凭一句话把不存在的商品变出来，也不能自己决定商品价格。它会先查询目录，把查到的真实参考号交给加购工具。商品找不到或规格不唯一时，系统会要求澄清。

“这套分工让自然语言能进入现有 ERP 流程。我们不需要为了聊天功能重新实现一套商品、购物车和结账系统。”

### 第 3 段：一次对话实际发生什么，约 3 分钟

“我们看一句完整的话：‘帮我下单一个黑色抽屉。’

“第一步，网站保存这条聊天消息，识别这个会话关联的 AI Agent。Agent 可以理解为配置好的购物助手，它有使用的模型、业务规则和允许调用的工具。

“第二步，Odoo 把客户当前的话、最近对话以及可用工具说明提交给模型。模型识别出这是购买请求，数量是 1，商品描述是黑色抽屉。

“第三步，模型提出调用商品搜索工具。Odoo 查询当前网站的已发布可售商品，返回真实商品名称、参考号和规格。如果匹配唯一，模型就调用加入购物车工具，把真实参考号和数量交给 Odoo。

“第四步，Odoo 执行标准购物车更新，返回实际增加的数量和提示，购物助手再据此回复客户，并提供购物车链接。

“所以，聊天中‘已加入’的依据应当是工具执行结果；现场演示时我们还会打开购物车，展示实际商品行。”

### 第 4 段：我们模块增加了什么，约 2 分钟

“Odoo 19 企业版在这个项目中提供了 AI Agent、对话、工具调用和网站客服集成的基础能力。我们的模块在这套框架上增加了购物业务工具与工作规则。

“目前模块有三个工具。第一个搜索当前网站真实商品，不增加购物车商品；第二个把已经明确的商品与数量加入当前网站购物车；第三个服务于内部使用场景，创建草稿销售报价单。

“网站购物与内部报价使用不同流程。网站客户使用的是购物车工具。内部报价工具按当前执行用户关联的客户创建草稿报价，不是让销售员在当前版本中任意指定其他客户，也不会直接确认订单。

“这次客户演示主要介绍前两个网站工具。它们组成从自然语言需求到真实购物车的流程。”

### 第 5 段：商品规格不明确时怎么处理，约 2 分钟

“客户说‘白色桌子’，不一定已经描述完整。实际商品可能还区分桌腿材质、尺寸或其他属性。如果目录中有多个符合描述的变体，助手应该列出真实可选规格，询问缺少的属性，然后再加购。

“这种追问是在帮助客户选对商品。相反，如果客户给了完整参考号，或者描述只匹配到一个实际可售商品，而且数量也明确，就可以直接加入购物车。

“我们的处理同时考虑商品模板和具体变体。例如沙发这个模板下面有不同材质，最终加入购物车的是具体材质变体。客户使用中文、目录采用英文时，助手也可以通过检索真实目录完成衔接；如果无法可靠识别，就继续问清楚，不应猜一个最接近的商品。”

### 第 6 段：执行如何受控，约 2 分钟

“AI 能执行的动作来自我们预先配置的工具。模型提出工具名称与参数，Odoo 再校验参数，并执行固定业务方法。这个功能没有给模型任意执行数据库命令的入口。

“网站商品查询会限定已发布、可销售和当前网站允许的商品范围。加入购物车前，会先检查整批商品和数量；执行中如有异常，会回滚本次批量操作，避免第三件商品失败而前两件已经加进购物车。

“需要准确区分的是，这个保护针对一次失败的批量加购。当前还没有数据库级的跨请求重复提交去重：成功后再次执行同样的加购，数量会继续增加。这也是我们在工作规则中要求助手成功后不要无故重复执行的原因。

“客户最后通过购物车核对商品，确认地址、税费、配送和付款。当前交付的工具范围到加入购物车为止。”

### 第 7 段：当前部署与响应体验，约 2 分钟

“当前项目的网站 Agent 已接入独立适配模块发现的 DeepSeek 文本模型，用于文本理解和工具调用。模型适配层与业务工具分开，因此业务逻辑可以保留，模型供应商可以根据项目需求调整；每次调整都要重新验证中文理解、工具调用、速度和费用。

“一句问题可能需要多次模型请求：先理解并搜索，再阅读搜索结果并加购，最后生成回复。因此响应时间受到模型服务和网络影响，不应承诺所有问题都立即完成。

“商品查询直接读取 Odoo 目录，当前下单流程不需要先训练模型记住全部商品。若客户还希望回答手册、制度或 FAQ，可以选用支持资料检索的模型，或另行开发检索组合。本版 DeepSeek 只支持文本与工具，会阻止关联知识 Sources；图片、PDF 和实时库存问答也不属于已交付能力。”

### 第 8 段：为什么把 DeepSeek 适配作为方案的一部分，约 3 分钟

“很多客户会优先考虑模型 API 预算，因此我们把 DeepSeek 放进模型选型和交付范围一起介绍。历史验证使用的是旧 deepseek-chat 标识的中文文本理解和工具调用，它能承接查询商品、读取结果、再执行加购这条流程。新目录型号需重新验证，我们会用客户自己的目录和常见表达来比较准确性、响应时间与实际费用。

“接入模型需要一段适配代码。它先告诉 Odoo 哪些模型属于 DeepSeek，再把 Odoo 的对话和工具说明转换为 DeepSeek 接口需要的格式，带上客户自己配置的 Key 发出请求。模型返回工具名和参数后，适配代码将它们交给 Odoo 的统一工具执行机制；真实业务结果再回传模型，形成完整对话。

“所以，支持 DeepSeek 不等于只添加一个 Key。模型接入现在由独立模块 ai_deepseek 提供，商品查询与加购由 ai_sale_order_2nd 提供。企业版 AI 核心已还原，无需维护那两处 DeepSeek 补丁。给客户新建环境时，安装需要的模块，在 AI 设置中填写客户 Key，再配置 Agent、主题、网站入口和目录并验收。两个模块互不依赖，DeepSeek 也能用于其他业务 Agent。切换网站 Agent 的模型不会同时切换所有其他 AI 自动化入口。

“成本也要按业务结果看。客户说一句话，可能先后经历搜索、加购和总结，多次调用的输入、输出和失败重试都会产生用量。我们建议比较‘完成一次正确加购的实际模型费用’，结合延迟和效果选择，而不只比较一项模型单价。供应商价格会变化，本材料不承诺固定价格或永远更便宜。

“当前验证不包含所有模型功能。自动发现的新型号需单独验收，旧 Reasoner 兼容路径还没有与历史 Chat 相同的下单验收；当前路径拒绝直接文件、独立结果 Schema、联网、embedding 和语音。没有登记未经验证的向量模型，DeepSeek Agent 也不能关联 Sources。如需资料库，需要选择已有支持的方案或另外开发。”

### 第 9 段：如何扩展和验收，约 2 分钟

“后续可以围绕已经验证的基础能力分阶段扩展，例如商品实时价格与库存查询、查询客户自己的订单、修改购物车数量、专门的订单确认流程，以及更完整的操作记录和重复提交保护。

“这些功能需要明确数据范围、客户身份和业务权限，并开发对应工具。特别是订单确认、收款和退款这类会直接改变业务状态的动作，需要单独设计授权与审核方式。

“验收时，我们建议同时看三类结果：客户表达需求是否顺畅；工具是否对真实目录和购物车产生预期影响；异常或不明确的情况是否能够追问并保持数据正确。接下来我们用几个实际场景演示。”

## 三、5 分钟现场演示

### 演示 A：唯一商品直接加购，约 90 秒

**输入：**

> 帮我下单一个黑色抽屉。

**预期过程：**搜索真实目录；匹配唯一已发布商品；保留原始消息中的数量 1；加入当前购物车并返回购物车链接。

**演示动作：**打开 `/shop/cart`，展示黑色抽屉的真实商品行与实际数量。当前测试目录的参考号为 `FURN_8900`。如果车里演示前已有该商品，应比较增加前后的数量，而不是只看总数量是否为 1。

**讲解：**“客户没有提供内部参考号，助手先查询目录，再用目录中的真实商品执行加购。”

### 演示 B：规格歧义追问，约 90 秒

**输入：**

> 帮我买一张白色可定制化桌子。

**预期过程：**在当前测试目录存在多个符合描述的变体时，列出真实材质等属性，询问缺少的规格。此时不应任意选一个变体加入购物车。

**后续动作：**依据 AI 列出的实际选项补充规格；只有描述已对应到唯一可售商品后再加购。演示前应验证当前目录中的实际选项，避免脱离目录预编答案。

**讲解：**“客户已经说了颜色和数量，但目录还区分其他属性。助手把缺失的信息问清楚，这有助于减少选错商品。”

### 演示 C：多个商品批量加购，约 90 秒

**使用已经实际验证的输入：**

> 帮我下单 DESK0005、DESK0006 各一个，再加一个 Two-Seat Sofa 天鹅绒。

**预期过程：**保留两个已知参考号；通过沙发目录识别实际 `Velvet` 变体；使用真实完整名称 `Two-Seat Sofa (Velvet)`；把三个明确商品各增加 1 件。

**演示动作：**打开购物车核对三项商品。演示 A、B 的既有商品也可能仍在车中，应说明这是同一个购物车累积结果，或在标准界面预先清空后单独演示。

**讲解：**“既支持已知型号，也支持用自然语言补充规格；最后执行的仍是实际目录商品。”

### 收尾：展示标准结账入口，约 30 秒

从购物车进入网站标准结账入口，说明客户可在这里核对客户信息、地址、价格、税费和配送，再按网站原有支付方式完成购买。停在演示合适的位置，不提交真实支付。

如果时间允许，可追加“添加一个不存在的商品”场景：预期找不到并说明需要补充信息，不能虚构成功，也不能改变已有商品数量。

## 四、现场异常时的备用讲解

| 现场情况 | 建议处理 | 可直接使用的话术 |
| --- | --- | --- |
| 一直显示思考中、模型暂时不可达 | 不连续提交同一句话；先核对车是否已有变化，再由技术人员查看消息与接口日志；使用脱敏成功材料解释 | “这一轮需要调用模型服务，当前响应有延迟。我们先看业务执行记录，避免重复提交导致数量增加。” |
| AI 追问规格 | 展示真实候选，补充缺少的属性 | “当前描述对应多个实际规格，系统正在把选择问清楚。” |
| AI 追问已提供的数量 | 明确补充一次数量，记录原句用于后续回归；不把它解释成必然设计行为 | “数量在原句中已经给出，这次模型没有完整保留。我们会把这句加入回归用例。” |
| 商品未找到 | 检查发布状态、当前网站、参考号、名称和翻译；使用会前验证的目录商品演示 | “助手只能执行真实目录中的可售商品，我们先核对当前网站实际发布的目录。” |
| 回复成功但车里没看到 | 核对浏览器、账号、域名与会话；看实际工具结果，不立即重复加购 | “购物车跟当前网站会话关联，我们核对一下聊天与购物车是否使用同一个会话。” |
| 老聊天转人工后不再回复 | 使用配置验证过的新 AI 会话；核对旧频道的 Agent 关联 | “这段会话已经转到人工客服，我们切回 AI 接待会话继续演示。” |
| 同一商品数量比预期多 | 检查演示前已有数量和成功调用次数；在标准界面调整 | “加购是继续增加数量。我们先核对已有数量与这几次操作，再调整到演示所需数量。” |

避免把所有异常都说成网络问题。实际原因可能在入口配置、模型、商品目录、权限、会话或工具业务执行的不同位置。

## 五、客户常见问答

### 1. 这是一个独立聊天机器人，还是 Odoo 的一部分？

当前项目复用 Odoo 19 企业版 AI 与网站客服框架，在其中配置购物助手并扩展业务工具。商品和购物车仍使用 Odoo 数据与业务流程。

### 2. 是不是要训练模型才能认识我们的商品？

当前实现不要求对商品目录进行模型微调。AI 负责提取客户意图和关键词，工具实时查询 Odoo 目录，返回真实参考号和具体变体。商品命名、属性、翻译和发布状态的质量仍会影响体验。

### 3. AI 会编造一个商品放进购物车吗？

购物车工具会在执行前匹配真实可售商品。找不到或匹配多个变体时会报错或要求澄清，不能仅靠模型编写一个商品名称就直接加购。最终商品行也可以在购物车核对。自然语言理解仍有概率性，需要持续对真实业务表达进行回归。

### 4. 价格和库存由谁决定？

购物车价格、税务等由已安装并配置的 Odoo 商城业务逻辑计算。当前专用搜索工具返回名称、参考号和属性，没有价格及实时库存字段。自然语言准确报价和库存问答需要专门工具与验收；是否限制缺货加购取决于库存相关模块与网站配置。

### 5. 加入购物车就代表订单确认了吗？

网站购物车底层可能对应草稿销售单，但加入购物车不代表销售单已经确认，也不代表已付款、开票或发货。客户仍需经过标准结账流程。

### 6. 能直接为客户确认订单和收款吗？

当前网站工具只实现加入购物车。订单确认、开票、支付、退款等需要单独开发工具，并明确用户授权和业务审核方式。

### 7. 可以查询和修改以前的订单吗？

这不是当前模块已经交付的工具。后续可以扩展，但应先认证客户身份，并把数据范围限制在该客户允许查看或操作的订单。

### 8. 可以删除商品、修改数量、应用优惠券吗？

当前专用工具只增加商品数量，没有删除行、设置总数量和优惠券接口。客户可以使用网站标准购物车界面操作；若要用聊天完成，需要新增相应工具。

### 9. 匿名客户能用吗？

在公开 Agent 和商城访问配置允许的情况下，可以通过访客会话使用。若网站要求登录才能购物，工具也会检查该限制。匿名与登录用户、不同浏览器和不同域名的会话不能简单视为同一个购物车。

### 10. 客户数据会发送到哪里？

模型调用会把当前问题、必要的会话上下文、工具说明和工具返回结果发给已配置模型服务。Odoo 当前核心还可能加入已登录用户的姓名、职位、邮箱和电话等上下文。上线前应明确允许发送的数据、供应商部署与数据处理要求，必要时精简上下文。演示材料和日志不得包含实际 API 密钥。

### 11. 能不能使用本地模型或换供应商？

架构允许在模型适配层接入其他服务。当前项目已适配并验证的是网站 Agent 的 DeepSeek Chat 文本与工具调用流程；接入其他服务需核对接口、工具调用能力、成本和速度，再做端到端验证。修改一个 Agent 的模型，也不代表所有 AI 自动化功能都会一起切换。

### 12. 是否已经具备知识库、图片或 PDF 问答？

Odoo 框架提供知识库等能力，但本版 `ai_deepseek` 只支持文本与工具，明确拒绝文件、向量服务和 Sources。要做手册问答，应选择已支持的 Provider 或另行开发检索组合。公开客服 Agent 只应接入适合向客户公开的资料。

### 13. 为什么有时需要等几秒或更久？

一次请求可能多次经过模型服务，例如先搜索再加购再总结，耗时会叠加。目录大小、会话长度、工具数量、模型服务和网络都会影响速度。应以实际业务场景测试响应时间，不使用未经测量的固定秒数承诺。

### 14. 费用怎么算？

费用通常包括 Odoo 相关许可与部署、实施开发维护，以及模型 API 使用费。若启用知识库，还可能有资料处理和向量计算费用。实际以供应商和合同计费为准；一条聊天消息可能对应多次模型调用。

### 15. 系统会记住客户所有历史吗？

聊天消息可由 Odoo 保存，但模型每次处理只读取配置的历史窗口；当前核心默认读取最近约 20 条历史消息。它不是自动训练，也不能据此承诺跨账号、跨浏览器的永久记忆。

### 16. 已经做了哪些验证？

当前模块已有 14 个业务回归测试，覆盖商品变体、网站范围、批量成功、失败回滚、数量校验、跨语言目录搜索等。此前实际模型验证还覆盖“一个黑色抽屉”和“三项商品批量加购”。这些验证说明已测试场景可用，并不等于所有用户表达、所有商品类型都已覆盖。

### 17. 只把系统参数改成 DeepSeek Key，就可以使用 DeepSeek 吗？

还需要安装独立 `ai_deepseek`，由它增加自动模型目录、独立请求服务和 AI 设置中的 Key 输入项。保存 Key 并同步目录后，Agent 选择当前可用型号并关联正确 Topic；购物场景还要安装业务模块。Key 只负责接口身份认证。既有 `ai.deepseek_key` 直接复用，其非空值优先于进程环境变量 `ODOO_AI_DEEPSEEK_TOKEN`。

### 18. DeepSeek 更便宜，是否就代表整体运行费用最低？

对模型 API 预算敏感时，DeepSeek 可以作为优先评估候选，但需要结合供应商当日价格、实际用量和业务成功率。一次业务可能调用模型多轮，长上下文、重复搜索和失败重试也会增加费用。建议在相同验收集上记录总模型费用、正确加购次数、延迟和错误情况，计算“测试总模型费用 ÷ 正确完成的加购次数”。明确该指标是否包含全部尝试成本，并另外列出许可、部署、维护和资料处理费用。缓存命中等计费项按供应商账单分类统计，不能把同一输入重复计费。本材料没有提供未经核实的价格或节省比例。

### 19. 迁移到客户环境时，需要交付哪些内容？

需要匹配版本和授权的 Odoo AI 基础、网站及商城模块，独立 `ai_deepseek`、购物模块 `ai_sale_order_2nd`，以及配置和验收说明。客户配置自己的凭据、模型、Topic、网站频道与发布商品。核心 DeepSeek 修改已还原，交付时维护两个独立模块及扩展点兼容性。文档资料压缩包只包含讲解材料，不是完整安装包。若卸载适配，原 DeepSeek Agent 会切回 `gpt-4o`，保留 Agent、Topic、历史与 Key；继续使用需要有效 OpenAI 配置。

### 20. 选择 DeepSeek 后，知识库和全部 AI 功能是否也一起可用？

不会一起开放。当前已验证 `deepseek-chat` 的文本与工具调用；`deepseek-reasoner` 尚需同等业务验收。适配拒绝文件、独立结果 `schema`、联网、embedding 和语音，并禁止 DeepSeek Agent 关联 Sources；工具参数 Schema 仍用于函数调用。其他 AI 自动化有各自模型路径。客户若需要这些能力，应另行选择或开发相应服务并验收。

### 21. 网站上的 AI 聊天框是你们开发的吗？

当前使用的是 Odoo 19 企业版原生聊天及 AI 集成。右下角客服由 `im_livechat`、`website_livechat` 和 `ai_livechat` 等模块提供，页面 AI 聊天区块由 `ai_website_livechat` 提供。我们的业务模块复用入口，定制的是商品查询、规格匹配、批量加购和相关工作规则；DeepSeek 则通过项目当前适配接入。完整交付包括基础模块、适配、业务工具和实际配置，不能只用“聊天原生”概括为全部方案安装即用。

## 七、建议记录的试点指标

在试点阶段记录“用户原句、实际工具选择、商品是否正确、数量是否正确、是否合理追问、购物车结果、模型与调用轮数、供应商实际用量和费用、耗时、异常原因”。可以统计明确需求的加购成功率、错误商品加入率、合理追问比例、一次正确加购的模型成本和进入结账的比例。

会议不宜直接承诺固定转化率或节省百分比。先用客户真实目录与常见表达建立验收集，再与试点前流程进行比较。
